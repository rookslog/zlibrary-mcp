# Review: Phases 20–21 (Quality Scoring Harness & CI Reporting)

**Date:** 2026-07-24
**Reviewed against:** the v1.3 milestone plan (QUAL-01…04) — requirement definitions and
revised acceptance criteria are preserved in the appendices at the end of this document
(the original planning tree has since been removed)
**Verdict:** Sound goals, but the plans assume greenfield where machinery already exists.
Recommend resequencing and one added prerequisite before execution.

---

## Summary

Phases 20 and 21 target the right outcome: quality that is *measured over time* rather
than asserted pass/fail. Two problems with the plans as written:

1. **Roughly 60% of Phase 20's stated deliverable already exists**, spread across three
   places the roadmap does not mention. Executing the phase as written would build a
   third overlapping system.
2. **An orphaned 337-line harness already implements Phase 20's headline artifact** —
   badly, and in a way that cannot run in CI. Its fate needs deciding *first*, or the
   phase ships a competitor to it.

There is also one trap worth designing against explicitly, covered in §4.

---

## 1. What already exists

| Phase 20 success criterion | Existing implementation | Gap |
|---|---|---|
| "body completeness" metric | `__tests__/python/test_recall_baseline.py` — line-level recall plus a 95% gross-length floor, across **17 documents** in `body_text_baseline.json` | Emits pass/fail, not a score |
| "footnote metrics" | `test_real_footnotes.py`, `test_inline_footnotes.py` against v3 ground truth for 4 documents | Same — assertions, not scores |
| "structure preservation" metric | **Nothing** | Genuinely new; no ground truth exists either |
| "machine-readable JSON report" | `scripts/run_rag_tests.py::generate_report()` writes `rag_test_report.json` | Requires live downloads; see §2 |
| "regenerate the baseline intentionally" | `scripts/generate_recall_baseline.py` (72 lines) | Undocumented, but functional |
| ground-truth corpus | 11 files in `test_files/ground_truth/`, incl. `schema_v3.json` | Fine |

So the corpus, the body-completeness metric, the footnote metrics, and a JSON reporter all
exist. What is genuinely missing is narrower than the phase implies:

- **Nothing aggregates them.** Metrics live inside pytest assertions, so the only output is
  green or red.
- **Pass/fail cannot show drift.** Quality can degrade 4% without crossing the 95% floor,
  and nothing surfaces that. This is the actual motivation for the phase and worth stating
  as the goal directly.
- **Structure preservation has no metric and no ground truth.** This is the real work in
  Phase 20, and the plan does not budget for creating ground truth.
- **No baseline comparison** (correctly Phase 21's job).

**Recommendation:** reframe Phase 20 from "build a scoring harness" to "extract the metrics
that already exist into callable functions, aggregate them, and add the one metric that
doesn't exist." Concretely: move the scoring logic out of `test_recall_baseline.py` into
`lib/rag/quality/scoring.py`, have the existing tests call it, and add a thin CLI that emits
the aggregate report. One source of truth. If the extraction is done right, the existing
tests get shorter, not longer — a useful signal that this is refactoring rather than
addition.

---

## 2. Prerequisite: decide the fate of `scripts/run_rag_tests.py`

This 337-line script already produces "a machine-readable JSON quality report" — QUAL-02
almost verbatim. It is unusable as-is, for reasons that matter:

- **It requires live downloads.** `from lib.python_bridge import download_book`, called
  per manifest entry. So it cannot run in CI, cannot run offline, and cannot run when
  Z-Library is unreachable — which, per the health assessment, is unverifiable right now.
- **It scores a different code path than the tests do.** It imports `process_pdf` from
  `lib.rag_processing`, the legacy facade, while `test_recall_baseline.py` imports from
  `lib.rag.orchestrator_pdf`. Two scoring paths that can disagree is worse than one.
- **It is an orphan.** No reference in `.github/`, `package.json`, or `pytest.ini`; the
  only mentions are in `docs/rag-robustness-enhancement-spec.md`. Yet 25 tests in
  `test_run_rag_tests.py` maintain it.

Building Phase 20 beside this leaves the repo with two JSON quality reporters, one of them
dead. **Add an explicit task 20-00: retire it, or split its download step from its scoring
step and reuse the scoring.** Retiring is likely correct — the download-and-score workflow
is what `download_book_to_file` plus the new scoring CLI would cover between them — but
that is a decision to make deliberately, with the 25 tests removed or repointed in the same
change.

---

## 3. Phase 21: right idea, wrong trigger

"Threshold behavior defaults to informational mode" is exactly right and worth keeping.

The problem is **where** it runs. Phase 21 says "CI runs the scoring harness". The full
pytest suite already takes **11m43s** on the runner (`test-full`, 20:06:13 → 20:17:56 on
run 24531364369), and the corpus tests are 119 of them. Adding corpus scoring to every push
grows the slowest job further, for a signal that is inherently trend-shaped rather than
per-commit.

**Recommendation:** run the scoring harness on a **schedule**, not per-push — the same
pattern as the Upstream Contract Check added in this cycle. Publish the artifact, compare
against the stored baseline, and let it file or update a rolling issue when a metric moves
beyond tolerance. A quality trend belongs on a cadence; a unit test belongs on a commit.
Keep `workflow_dispatch` so a maintainer can score a branch on demand before a release.

This also resolves the informational-vs-blocking tension cleanly: a scheduled job that
files an issue is *already* the informational mode, with no threshold plumbing needed to
get there.

---

## 4. The trap: a harness that silently scores nothing

Worth designing against explicitly, because it would present as success.

The corpus PDFs live in Git LFS. A checkout without LFS leaves pointer files, and as of
this cycle the test suite **skips** on those rather than failing (a deliberate improvement —
the previous behaviour was five misleading assertion errors). A scoring harness built on
the same fixtures would therefore find zero scoreable documents, compute no regressions,
and report a clean run.

A quality gate that reports "no regressions" because it measured nothing is worse than no
gate, because it is trusted.

**Recommendation:** add a success criterion to Phase 20 — the report must state how many
documents were scored and how many were skipped and why, and the runner must exit non-zero
if the scored count is below an expected minimum. Then add to Phase 21 that the CI job
asserts the scored count matches the corpus size, so a checkout misconfiguration fails
loudly instead of passing quietly.

---

## 5. On `page_analysis_map`

Phase 21 currently carries "`page_analysis_map` is either integrated into the
scoring/reporting path or explicitly documented as out of scope." That is an open question
parked inside a delivery phase, and it will either expand the phase unpredictably or be
resolved with a one-line dismissal to satisfy the criterion.

**Recommendation:** decide it before planning Phase 20, since the answer changes what the
report contains. It is a five-minute judgement, not a phase deliverable.

---

## 6. Recommended revisions

**Phase 20 — Quality Scoring Harness**

- Add task 20-00: resolve `scripts/run_rag_tests.py` (retire, or split and reuse).
- Reframe: extract existing metrics into `lib/rag/quality/scoring.py`; aggregate; do not
  build a parallel system.
- Add explicit scope for creating **structure-preservation ground truth** — the only
  genuinely new metric, and the phase's real cost.
- Add criterion: report includes scored/skipped counts, and the runner fails when the
  scored count is below the expected minimum.
- Decide `page_analysis_map` here rather than in Phase 21.

**Phase 21 — CI Reporting & Regression Controls**

- Change trigger from per-push to **scheduled + `workflow_dispatch`**, reusing the
  upstream-check pattern.
- Keep informational-by-default; implement it as a rolling issue rather than threshold
  plumbing.
- Add criterion: CI asserts scored count matches corpus size, so an LFS or checkout
  misconfiguration fails loudly.
- Remove the `page_analysis_map` criterion (moved to Phase 20).

**Sequencing unchanged** — 20 still precedes 21. The dependency is real.

---

## 7. What I did not change

The phase *goals* are good and I am not proposing rescoping them. Measuring RAG quality
over time is the correct next investment for this project: the pipeline is where the
differentiated value is, it has 119 corpus tests already, and pass/fail assertions are
genuinely the wrong instrument for tracking extraction quality. QUAL-01…04 as written
describe the right outcomes.

The revisions above are about not building things twice.

## Appendix A: Requirements reference

Preserved from the v1.3 milestone requirements (defined 2026-04-16) before the planning
tree was removed. These are the requirements Phases 20-21 exist to satisfy.

### Quality Scoring (v1.3 scope)

- **QUAL-01**: Maintainer can compute precision/recall-style quality metrics for body
  extraction, structure preservation, and footnotes against the ground-truth corpus.
- **QUAL-02**: Maintainer can emit a machine-readable JSON quality report from the
  scoring harness for local validation runs.
- **QUAL-03**: CI can publish the quality report artifact and compare it against a stored
  baseline so regressions are visible on every run.
- **QUAL-04**: Quality regression thresholds are configurable and default to
  informational mode until the baseline proves stable.

Mapping: QUAL-01 and QUAL-02 → Phase 20; QUAL-03 and QUAL-04 → Phase 21.

### Deferred beyond v1.3 (v2 candidates)

Tracked so they do not leak back into the active scope accidentally:

- **QUAL-F01**: Quality regression checks block PRs once the baseline is stable enough
  to trust as a hard gate
- **QUAL-F02**: CI publishes trend views over time instead of only per-run JSON artifacts
- **QUAL-F03**: Semantic chunking is added for embedding-model-ready RAG output
- **RAG-F01**: `page_analysis_map`-derived diagnostics become part of the public metadata
  contract if quality-scoring evidence shows they help downstream consumers

### Out of Scope

| Feature | Reason |
|---------|--------|
| Promoting `search_multi_source` to a public MCP tool | Already shipped and documented; not real v1.3 work |
| Breaking response-shape changes for `process_document_for_rag` or `download_book_to_file` | Existing clients and tests already depend on the current path fields |
| PR-blocking quality gates on day one | Baseline needs to stabilize before turning informational metrics into merge blockers |
| General RAG feature expansion beyond output/scoring | This milestone is refinement, not a new capability grab-bag |

## Appendix B: Acceptance criteria (revised 2026-07-24)

The success criteria for each phase as revised by this review. These supersede the
original phase definitions.

### Phase 20: Quality Scoring Harness

**Goal**: Aggregate the quality metrics that already exist into a repeatable scoring run,
and add the one metric that does not exist. **Requirements**: QUAL-01, QUAL-02.

1. `scripts/run_rag_tests.py` is resolved before new work begins — retired, or its
   download step split from its scoring step so the scoring is reused. It currently
   requires live downloads (so it cannot run in CI or offline) and scores through the
   legacy `lib.rag_processing` facade rather than `lib.rag.orchestrator_pdf`, giving two
   scoring paths that can disagree. Its 25 tests are removed or repointed in the same
   change.
2. Existing metrics are extracted into callable functions (`lib/rag/quality/scoring.py`)
   that the current tests call, rather than reimplemented alongside them — the existing
   tests should get shorter, not longer
3. Structure preservation is added as a metric, including the ground truth it needs,
   which does not exist yet — this is the phase's real cost
4. Local validation runs emit a machine-readable JSON report with per-document and
   aggregate metrics, reporting **trend-capable scores rather than pass/fail**, since
   quality can degrade several percent without crossing any existing threshold
5. The report states how many documents were scored and how many were skipped with
   reasons, and the runner exits non-zero when the scored count falls below an expected
   minimum. Corpus PDFs are Git LFS objects and the suite now *skips* on unhydrated
   pointers, so a harness without this check would score zero documents, find no
   regressions, and report a clean run — a false green that is worse than no gate
   because it is trusted.
6. The harness is documented well enough to regenerate or refresh the baseline
   intentionally rather than by accident
7. Whether `page_analysis_map` belongs in the report is decided here, since the answer
   changes what the report contains

### Phase 21: CI Reporting & Regression Controls

**Goal**: Surface RAG quality regressions on a cadence without turning unstable metrics
into noisy blockers. **Requirements**: QUAL-03, QUAL-04. **Depends on**: Phase 20.

1. The scoring harness runs on a **schedule** with `workflow_dispatch` for on-demand runs
   before a release, reusing the pattern established by
   `.github/workflows/upstream-check.yml` — not on every push
2. The job publishes the JSON report as an artifact and compares it against a stored
   baseline, making movement visible in the job output
3. Informational-by-default is implemented as a rolling issue rather than threshold
   plumbing — a scheduled job that files an issue *is* informational mode, and can be
   promoted to blocking later without redesign
4. The job asserts the scored document count matches the corpus size, so an LFS or
   checkout misconfiguration fails loudly instead of reporting a clean run over zero
   documents
